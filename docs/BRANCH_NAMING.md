# Branch Naming Convention

> This project's CI pipeline uses branch names to map work back to Jira stories.
> A branch must contain a **Jira key** for the AI agents to do their full job.

## TL;DR

Every branch in the AI pipeline should contain a Jira key (`PREFIX-NUMBER`) somewhere in its name.

| ✅ Good | ❌ Won't be picked up |
|---|---|
| `auto/PROJ-123-login-validation` | `feature/login-validation` |
| `feature/PROD-1234-add-checkout` | `bugfix/locked-out-users` |
| `bugfix/MOBILE-42-token-refresh` | `wip-jane-experiments` |
| `hotfix/INFRA-99-network-config` | `temp-branch-2026-05-05` |
| `PROJ-7-just-the-key-prefix` | `cleanup` |

## Why This Matters

Agent 5 (Reporter) needs to know **which Jira story to comment on** when tests run in CI. The cleanest way to convey that is to embed the Jira key in the branch name. Without a key:

- Agent 5 cannot post test results to Jira
- The pipeline will skip the reporting step (gracefully — it won't fail the workflow)
- The QA-to-engineering feedback loop is broken for that branch

## The Pattern

A Jira key has the form **`PREFIX-NUMBER`** where:
- `PREFIX` is one or more **uppercase letters** (the project key in Jira)
- `NUMBER` is one or more **digits** (the issue number)

Examples of valid prefixes from real teams:

| Team type | Example prefix | Sample full key |
|---|---|---|
| Single-team Scrum project | `SCRUM` | `SCRUM-123` |
| Product team | `PROD` | `PROD-1234` |
| Mobile team | `MOBILE` | `MOBILE-42` |
| Backend / API team | `BACKEND` or `API` | `BACKEND-100` |
| Infrastructure | `INFRA` or `OPS` | `INFRA-1` |
| Bug-tracking project | `BUG` | `BUG-456` |
| Customer / support | `CUSTOMER` or `SUPPORT` | `CUSTOMER-7` |
| Multi-prefix (multi-project) | varies | `PAYMENTS-32`, `WEB-7` |

The system **does NOT hardcode any prefix.** Whatever your Jira project's key is, it will be matched.

## Where the Key Can Appear in the Branch

The Jira key can appear anywhere in the branch name; the regex finds the **first** match:

```
✅ Beginning:    PROJ-123-feature
✅ After prefix: auto/PROJ-123-feature
✅ After prefix: feature/PROJ-123-foo
✅ In middle:    update-PROJ-123-stuff   (works, but ugly)
```

## Recommended Conventions

While the system is permissive, we recommend two patterns:

### 1. AI-generated branches (Agent 2 creates these)

```
auto/<KEY>-<short-feature-name>
```

Examples:
- `auto/PROJ-123-login-validation`
- `auto/PROD-1234-add-checkout`

The `auto/` prefix makes it visually obvious that the branch was generated by an AI agent. Agent 2's prompt is configured to follow this convention.

### 2. Human-created branches

```
<category>/<KEY>-<short-description>
```

Where `<category>` is one of `feature`, `bugfix`, `hotfix`, `chore`, etc.

Examples:
- `feature/PROJ-123-add-search`
- `bugfix/PROJ-456-fix-locked-out-user`
- `hotfix/PROD-99-urgent-database-failover`

## Validation in the Code

The project provides three utility functions in `config/__init__.py`:

```python
from config import (
    extract_jira_key,
    is_valid_branch_for_pipeline,
    assert_valid_branch_for_pipeline,
)

# Soft check — returns the key or None
key = extract_jira_key("auto/PROJ-123-foo")            # → "PROJ-123"
key = extract_jira_key("feature/no-key-here")          # → None

# Boolean check
is_valid_branch_for_pipeline("auto/PROJ-123-foo")      # → True
is_valid_branch_for_pipeline("feature/no-key-here")    # → False

# Strict check — raises InvalidBranchNameError if no key
assert_valid_branch_for_pipeline("auto/PROJ-123-foo")  # → "PROJ-123"
assert_valid_branch_for_pipeline("feature/no-key-here")  # → raises
```

### Where each is used

| Function | Used by | Behavior |
|---|---|---|
| `extract_jira_key` | Agent 5 (Reporter) | Find key for posting comment |
| `is_valid_branch_for_pipeline` | Agent 5 (Reporter) | Decide whether to skip or post |
| `assert_valid_branch_for_pipeline` | Agent 2 (Coder) | Fail FAST if Agent 2 generates a bad branch name |

## What Happens for Branches Without a Key

This is a **graceful skip**, not an error:

- The Agent 4 workflow runs as normal — tests still execute, results still go to GitHub
- The Agent 5 step logs a warning: `"Skipping Agent 5: branch has no Jira key"`
- The job exits with code 0 (no red ❌ on the PR)
- No comment is posted to Jira

This means humans can freely create branches without a Jira key (e.g., for quick experiments) without worrying about the pipeline failing.

## Edge Cases the Regex Handles

The regex `\b([A-Z][A-Z0-9_]*-\d+)\b` is intentional:

| Branch | Extracted | Why |
|---|---|---|
| `auto/PROJ-123` | `PROJ-123` | Standard case |
| `auto/PROJ-123-feature` | `PROJ-123` | Stops at the first match (greedy on letters/digits, anchored by `-`) |
| `feature/PROJ123-foo` | `None` | No hyphen between letters and digits — invalid Jira format |
| `PROJ-123abc` | `None` | Trailing letters mean it's not a clean key |
| `version-2-PROJ-99` | `PROJ-99` | Finds the key even after other dashes/numbers |
| `proj-123` | `None` | Lowercase — not a Jira key |
| `MULTI_WORD-42` | `MULTI_WORD-42` | Underscores in prefix are allowed (per Jira spec) |

## Summary Checklist

When creating a branch for AI-pipeline work, ask:

- [ ] Does my branch name contain a Jira key like `PROJ-123`?
- [ ] Is the prefix uppercase?
- [ ] Is there a hyphen between the prefix and the number?
- [ ] Does the key correspond to a real story/issue in Jira?

If all four are yes → ✅ ready to push, the AI pipeline will work.

If any are no → that's fine for ad-hoc work, but Agent 5 won't post to Jira for this branch.
